# Plan: Making Agents Asynchronous

## Executive Summary

This document outlines a comprehensive plan to transform the JARVIS agent system from a synchronous tool invocation model to a fully asynchronous, non-blocking architecture. The goal is to enable concurrent agent operations, background processing, and improved resource utilization.

---

## 1. Current State Analysis

### 1.1 Existing Architecture

The current system implements:
- **BaseAgent** (`core/agents/base.py`): Abstract base class with synchronous tool execution
- **CodingAgent** (`core/agents/coding_agent.py`): Main JARVIS agent for all tasks
- **ExploreAgent** (`core/agents/explore_agent.py`): Specialized subagent for codebase exploration

### 1.2 Current Limitations

1. **Sequential Tool Execution**: Tools are executed one at a time in a blocking manner
2. **No Concurrent Operations**: Multiple agents cannot run simultaneously
3. **Limited Background Processing**: Background processes exist but are not integrated with agent workflows
4. **Synchronous LLM Calls**: LLM generation blocks the main thread
5. **No Task Prioritization**: All operations have equal priority
6. **Limited Scalability**: Cannot handle multiple user requests concurrently

### 1.3 Current Asynchronous Features

The system already has some async foundations:
- `async/await` pattern used throughout
- Background process management (`list_background_processes`, `read_background_output`)
- Streaming support for LLM responses
- Async tool execution in some tools

### 1.4 Actual Codebase Analysis

Based on the codebase analysis, the current implementation includes:

**Key Files:**
- `core/agents/base.py`: Contains `BaseAgent` class with async methods like `_process_with_tools()`
- `core/agents/explore_agent.py`: `ExploreAgent` subclass with specialized exploration capabilities
- `core/tools/agent_tools.py`: Contains `InvokeAgentTool` and `ActivateSkillTool`
- `core/tools/background_tools.py`: Background process management tools

**Current Async Patterns:**
- Streaming: Uses `AsyncGenerator` for streaming LLM responses
- Tool execution: Already has async patterns in `_process_with_tools()` method
- Message handling: Uses standard message roles (system, user, assistant)
- Callback system: Has `stream_callback`, `tool_call_callback`, `tool_result_callback`

**Key Insight:** The system is already partially async but needs:
1. Concurrent agent execution (multiple agents running simultaneously)
2. Concurrent tool execution (multiple tools in parallel)
3. Better integration of background processes with agent workflows
4. Resource monitoring and management
5. Task prioritization and queuing

### 1.5 Current Tool System Details

**Tool Categories:**
| Category | Tools | Description |
|----------|-------|-------------|
| File Operations | FileReadTool, FileWriteTool, ListDirectoryTool, GlobTool | File I/O operations |
| Code Operations | BashTool, RunTestsTool, REPLTool, PowerShellTool | Code execution |

**Tool Execution Pattern:**
- Tools have `execute()` method returning `ToolOutput`

### 1.6 LLM Provider Integration

The system uses `BaseLLMProvider` from `core.llm.base` with:
- `generate()` method for non-streaming responses
- `generate_with_tools()` method for tool calling
- Support for both sync and async generation
- Model selection via `model` parameter
- Streaming support via `AsyncGenerator` chunks

The streaming response format includes:
- `text` chunks for content
- `reasoning` chunks for chain-of-thought
- `tool_calls` for function invocations
- `tool_call` for individual tool calls

## 2. Goals and Objectives

### 2.1 Primary Goals

1. **Enable Concurrent Agent Operations**: Multiple agents can run simultaneously without blocking
2. **Non-Blocking Tool Execution**: Tools execute asynchronously without blocking the agent loop
3. **Background Task Support**: Agents can delegate long-running tasks to background processes
4. **Improved Resource Utilization**: Better CPU and memory usage through concurrent operations
5. **Enhanced User Experience**: Faster response times and progress feedback for long operations

### 2.2 Secondary Goals

1. **Task Prioritization**: Implement priority levels for different types of operations
2. **Resource Monitoring**: Track CPU, memory, and I/O usage during agent operations
3. **Graceful Degradation**: Fallback mechanisms when resources are constrained
4. **Observability**: Better logging and monitoring of async operations

### 3.1 Architecture Overview

```
└──────────────────────────────┬──────────────────────────────┘
                               │
                   ┌───────────▼───────────┐
                   │    Async Tool Pool    │

                               │
         ┌─────────────────────┼─────────────────────┐
         │                     │                     │
    ┌────▼────┐           ┌────▼────┐          ┌─────▼─────┐
    │  LLM    │           │  Tools  │          │ Background│
    │ Provider│           │  Pool   │          │ Processes │
    └─────────┘           └─────────┘          └───────────┘
```

### 3.2 Key Components

#### 3.2.1 AsyncAgentManager

A new component to manage agent lifecycle and task scheduling:
- **Task Queue**: Priority-based task queue for agent operations
- **Worker Pool**: Configurable pool of async workers
- **Resource Monitor**: Tracks system resources and adjusts concurrency
- **State Manager**: Manages agent states (idle, running, waiting, completed)

#### 3.2.2 AsyncToolExecutor

Enhanced tool execution with:
- **Concurrent Execution**: Execute multiple tools simultaneously
- **Timeout Management**: Configurable timeouts per tool type
- **Resource Limits**: Memory and CPU limits per tool
- **Retry Logic**: Automatic retry with exponential backoff

#### 3.2.3 BackgroundTaskManager

Dedicated system for long-running tasks:
- **Process Pool**: Dedicated process pool for CPU-intensive tasks
- **Task Tracking**: Monitor and report on long-running operations
- **Result Caching**: Cache results for frequently accessed operations
- **Cleanup Policies**: Automatic cleanup of old results

### Phase 1: Foundation (Weeks 1-2)

#### 4.1.1 Create Async Infrastructure

**File: `core/agents/async_manager.py`**
```python
class AsyncAgentManager:
    """Manages asynchronous agent operations and task scheduling"""
    
    def __init__(self, max_concurrent_agents: int = 5):
        self.max_concurrent_agents = max_concurrent_agents
        self.task_queue: asyncio.PriorityQueue = asyncio.PriorityQueue()
        self.running_agents: dict[str, BaseAgent] = {}
        self.semaphore = asyncio.Semaphore(max_concurrent_agents)
    
    async def submit_task(self, agent: BaseAgent, task: str, priority: int = 0):
        """Submit a task to the async queue"""
        await self.task_queue.put((priority, task, agent))
    
    async def start_processing(self):
        """Start processing tasks from the queue"""
        while True:
            priority, task, agent = await self.task_queue.get()
            async with self.semaphore:
                await agent.process(task)
```

**File: `core/tools/concurrent_executor.py`**

```python
class ConcurrentToolExecutor:
    """Execute multiple tools concurrently with resource limits"""
    
    def __init__(self, max_workers: int = 10):
        self.semaphore = asyncio.Semaphore(max_workers)
    
    async def execute_concurrent(self, tool_calls: list[tuple[str, dict]]) -> list[ToolOutput]:
        """Execute multiple tool calls concurrently"""
        tasks = [self.execute_single(name, args) for name, args in tool_calls]
        return await asyncio.gather(*tasks, return_exceptions=True)
    
    async def execute_single(self, name: str, args: dict) -> ToolOutput:
        async with self.semaphore:
            # Execute tool with resource limits
            pass
```

## 5. Risks and Considerations

### 5.1 Technical Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Race conditions in tool execution | High | Implement proper locking mechanisms |
| Memory leaks from background processes | Medium | Add cleanup policies and monitoring |
| Deadlock scenarios | High | Use timeouts and deadlock detection |
| Resource exhaustion | Medium | Implement resource quotas and limits |

### 5.2 Performance Considerations

1. **Thread Pool Size**: Configure based on CPU cores and I/O vs CPU-bound tasks
2. **Memory Management**: Monitor and limit memory per agent
3. **Connection Pooling**: Reuse connections for LLM and database operations
4. **Caching Strategy**: Cache frequently accessed data

### 5.3 Backward Compatibility

- Maintain synchronous API as fallback
- Provide migration guide for existing code
- Ensure all existing tests pass

```python
async def stream_response(self):
    for chunk in self.llm.stream():
        yield chunk
        await asyncio.sleep(0)

# Concurrent execution pattern
async def execute_parallel(self, tasks):
    results = await asyncio.gather(*tasks, return_exceptions=True)
    return [r for r in results if not isinstance(r, Exception)]

# Semaphore pattern for resource limiting
async def limited_operation(self, semaphore, operation):
    async with semaphore:
        return await operation()
```
